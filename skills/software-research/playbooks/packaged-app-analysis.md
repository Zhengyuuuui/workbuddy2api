# Playbook: Packaged Application Analysis

适用于把代码打包进壳/资源归档的应用（如以安装包、归档、托管运行时分发的应用）。
`Electron`、`Tauri` 等是它的常见实例，但不是本 Playbook 的前提——本 Playbook 关注
"代码被打包/压缩/归档在资源文件中"这一形态。

## 何时用
- Phase 2 分类结果为 Packaged Application。
- 发现应用主逻辑不在源码目录，而在某个资源归档/二进制包内。

## 识别形态
| 观察 | 含义 |
| -- | -- |
| 存在运行时壳可执行文件（名称含 Electron/Node/Deno 等） | 托管运行时应用 |
| 存在资源归档文件（.asar / .appx / 资源段） | 主代码在归档内 |
| 存在原生动态库 | 核心逻辑可能部分在原生层 |
| 存在解释型脚本包（.js / .py / .jar 等） | 代码可直接或半直接阅读 |

## 工作流

### 1. 定位代码载体
- 找到可执行入口与资源目录。
- 判断主代码载体是归档、脚本还是原生库。
- 用 `strings` 对载体做低代价扫描，收集 URL / 路径 / 标识符（见 `techniques/string-extraction.md`）。

### 2. 解包 / 提取
- 对归档使用对应提取工具（`.asar` → asar 工具；`.appx` → 解包工具；zip → unzip）。
- 解包后应得到可读目录树 + 配置文件 + 源码/字节码。

### 3. 定位高价值配置
- 搜索名称含 `product*`、`config*`、`manifest*`、`package*`、`settings*` 的文件。
- 这类配置文件常一次性给出：服务地址、认证方式、域名白名单、特性开关、可调用实体清单。
- 读配置要**原文引用**，标注来源文件与字段路径。

### 4. 模块定位
- 按目录/文件名推断模块归属（auth / client / core / config），但**用内容验证**，不靠文件名断言。
- 在压缩/混淆代码中，用正则提取关键路径、header、服务地址的上下文。
- 记录每个模块负责的职责与对外交互。

### 5. 关键逻辑还原
- 提取认证/核心行为相关配置块（type / prefix / header 名 / platform / domain 列表）。
- 还原端到端时序：方法、路径、必填 header、body、返回字段、状态机。
- 记录凭证的持久化位置与权限。

### 6. 运行时确认（必做）
- 静态声明的服务地址 ≠ 运行时实际使用的地址。
- 读取应用的数据目录、本地存储、缓存（`strings` / 解析），确认运行时值：
  已登录账户、实际服务地址、可用的可调用实体清单、环境覆盖。
- 若静态与运行时不一致，**记录冲突**并以运行时为准进行验证。

### 7. 动态验证
- 用无凭证请求探测协议可达性（应返回明确的协议响应而非连接失败）。
- 用还原的流程完成一次真实交互，获取有效凭证。
- 用凭证实测目标功能，逐项记录成功/失败。
- **倾向直接执行**：解包、读配置、扫字符串、读缓存、探测，都是对自身已装软件的常规研究，
  授权判定过一次就放开做，不要反复自我设限。

## 常见错误
- 只解包不读取内容就下结论。
- 压缩代码未解码就搜不到关键路径。
- 把静态配置地址当运行时事实（运行时可能被云端/环境覆盖）。
- 忽略应用的数据/缓存目录（运行时真相所在）。
