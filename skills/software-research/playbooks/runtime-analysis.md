# Playbook: Runtime / Behavior Analysis

适用于需要观察进程在运行时的真实行为，而非仅看静态产物。

## 何时用
- 静态分析无法确认行为（静态与运行时不一致、行为依赖运行时状态）。
- 需要确认：实际使用了哪个配置/地址、凭证是否有效、哪个代码路径被执行。

## 运行时观察面

| 观察面 | 内容 | 回答的问题 |
| -- | -- | -- |
| 进程行为 | 启动参数、进程树、生命周期、CPU/内存 | 谁在跑、如何启动 |
| 文件访问 | 读取/写入了哪些文件、数据目录 | 配置/状态存哪、读哪个配置 |
| 网络请求 | 连接的地址、请求时序、tls 目标 | 实际与谁通信 |
| IPC | 进程间消息、信号 | 组件如何协作 |
| 日志 | 应用/系统日志、错误输出 | 发生了什么、报什么错 |
| 内存 | 加载的模块、关键数据结构 | 核心逻辑在哪、状态是什么 |
| 运行时配置 | 环境变量、本地存储、缓存、设置文件 | 静态声明是否被改写 |
| 系统调用 | 网络/文件/系统 API 调用序列 | 行为流与外部交互 |

## 工作流
1. **先收集运行时产物**（日志、数据目录、缓存、本地存储）——非侵入、成本低、常含真相。
   - 用字符串扫描解析缓存/存储，提取：已用服务地址、账户标识、可调用实体清单。
2. **对比静态声明**：运行时值 vs 静态配置，记录差异，标出待验证点。
3. **必要时运行/附加目标**：观察文件、网络、进程变化。
4. **设计受控实验**：改动输入/环境变量/配置，观察行为是否变化，验证因果。

## 方法原则
- 优先非侵入式（读日志、读缓存）再考虑侵入式（附加/插桩）。
- 运行时证据能把结论从 Hypothesis 升级为 Confirmed。
- 目标"已经解释清楚"即停止，不无限扩展观察。

## 常见错误
- 只分析静态产物，忽略数据/缓存目录（丢失运行时真相）。
- 静态与运行时冲突时不记录、不裁定。
- 无目的地长时附加而不设计实验。
