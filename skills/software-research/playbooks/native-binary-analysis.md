# Playbook: Native Binary / Dynamic Library Analysis

适用于编译型可执行文件与动态库。关注符号、字符串、调用关系与外部交互的还原。
本 Playbook 提供方法层指引，具体工具取决于目标平台与架构。

## 何时用
- Phase 2 分类结果为 Binary / Bytecode / Dynamic Library。
- 目标是原生可执行、动态库、固件或字节码。

## 观察层（按成本从低到高）

### 1. 文件识别
- 识别文件类型、架构、入口点、导入/导出表（动态库尤其关注导出符号）。
- 记录编译器/打包器指纹、是否加壳、是否 strip 符号。

### 2. 字符串与符号收集
- 提取可读字符串（URL、路径、报错信息、标识符、参数名）——低成本高信号。
- 收集符号表 / 导出符号 / 导入函数，建立"调用了谁"的初步图。
- 若被 strip，退化为纯字符串 + 行为分析。

### 3. 结构理解
- 识别关键代码区段、数据区段、只读配置区段。
- 定位与外部交互（网络、文件、系统调用）相关的代码位置。

### 4. 反汇编 / 反编译（按需）
- 在符号/字符串不足以回答问题时使用。
- 从"对外交互点"（导入函数调用处、网络库、系统 API）反推上游调用链。
- 目标是用代码确认行为，而非通读所有汇编。

### 5. 动态观察（必要时）
- 加载/运行目标，观察文件访问、网络连接、进程状态、环境变量影响。
- 用运行时证据确认静态分析中的推测。

## 方法原则
- 先字符串/符号（低代价），再反汇编（中代价），再完整反编译（高代价）。
- 从**对外交互点**反推逻辑，而不是线性通读。
- 静态结构只产生 Hypothesis / Strong Evidence；行为需运行时或清晰调用确认。

## 常见错误
- 一上来就完整反编译（成本高、信息密度低）。
- 被 strip 符号的二进制误导（以为无法分析）。
- 把导入表"可能调用"当作"确实调用"。
