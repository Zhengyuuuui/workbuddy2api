# Case Study: 还原 AI 客户端私有后端协议

> 本文是对本 Skill 通用方法论的一次真实实例演示，**不是核心工作流本身**。
> 目的：展示 SKILL.md 中的阶段/原则在真实目标上如何落地。
> 具体软件、公司、技术（Electron / OAuth / app.asar / proxy）仅供示意，不代表方法论的适用范围。

## 背景与问题
存在一个已知的、可用的同类客户端（产品 A）的协议实现；目标是让另一个未知客户端（产品 B，同门海外版）
复用到同一协议。公开文档不足，需要自行还原产品 B 的后端接口与认证流程。

## 研究路径（对应 SKILL.md 阶段）

| 阶段 | 实际动作 | 证据等级 |
| -- | -- | -- |
| P0 目标定义 | 拆解为：认证方式 / 端点在哪构造 / token 如何获取存储 / 模型如何调用 | — |
| P0 Reuse | 发现仓库已有产品 A 的客户端实现 → 提取协议（external-link 时序） | Confirmed（已有可运行代码） |
| P1 侦察 | 定位产品 B 安装目录与数据目录；判断为打包应用（运行时壳 + 资源归档） | Confirmed |
| P2 分类 | 分类 = Packaged Application | Confirmed |
| P2 字符串 | 对资源归档做字符串扫描，捞出自建服务地址与第三方 SDK 地址 | Strong Evidence |
| P3 解包 | 解包资源归档 → 得到目录树 + 产品配置文件 + 源码 | Confirmed |
| P3 配置 | 产品配置文件一次给出认证类型、路径前缀、域名白名单、可调用实体清单 | Confirmed |

| P9 证据链 | 每条结论标注来源（配置文件原文 / 命令输出 / 响应体） | — |

## 关键发现（方法论层面）
1. **Reuse 优先**：已有同门实现 → 直接从"复用 + 改参数"开始，而非从二进制重逆。
2. **静态 ≠ 运行时**：产品配置文件声明一个服务地址，运行时缓存/云端配置实际使用了另一个。
   这是"Strong Evidence 指向声明、Confirmed 需实测"的典型。规则见 `methodology/evidence.md`。
3. **配置是金矿**：产品配置文件一次性给出认证、地址、白名单、可调用实体清单。
4. **请求差异用响应体定位**：非 2xx 时读 code/msg，据错误信息修正请求（如补必需消息结构）。

## 失败路径（供校准）
| 尝试 | 结果 | 教训 |
| -- | -- | -- |
| 抓官方公开文档 | 只有产品介绍，无 API 文档 | 公开资料不足 → 转向本地静态分析（P3） |
| 对归档直接搜认证路径 | 只找到部分地址，无认证路径 | 需解包后对解码源码搜 |
| 客户端直接连接 | TLS 证书校验失败 | 运行环境的 CA 配置不足，需显式证书 |
| 无凭证拉取云端配置 | 返回错误提示缺标识头 | 读响应体定位缺失要求 |
| 调用单个未开放实体 | "未找到该实体" | 多属凭证未开放，非协议失败 |

## 经验总结
- 完整遵循"证据→假设→验证→更新模型"循环；每一步先问最低成本信息增益最高的动作。
- 静态信息负责产生假设，运行时证据负责确认事实。
- 复用、信息增益、证据分级是本案例真正可迁移的部分；具体软件与技术不迁移。
